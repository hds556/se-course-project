## 1. 需求与目标

卖家想知道"谁来买过、联系谁、买过什么"。

- **客户列表**＝系统里**全部注册账号**，注册即入列，与是否下单无关（BR-22）；不含游客。
- **客户购买历史**＝该客户**已终结**的下单记录（成功 / 失败）；排队中与交易中的不看这里，走「交易管理」按商品查（FR-S-08）。

不做的（EX-06，要求"不存在入口"）：
账号编辑 / 禁用 / 删除、导出、搜索与筛选。

## 2. 接口

### 2.1 `GET /api/admin/customers`（FR-S-13）

| 参数 | 默认 | 说明 |
| --- | --- | --- |
| `page` | 1 | 页码，从 1 起 |
| `size` | 10 | 每页条数，上限 50（与买家端 `/api/customer/orders` 同一口径） |

响应：

```json
{ "items": [ { "id": 2, "username": "buyer2", "phone": "13900000002",
              "defaultPlace": "未设置", "registeredAt": "2026-10-31T02:32:42.316Z" } ],
  "page": 1, "size": 10, "total": 2, "totalPages": 1 }
```

- 字段**恰好四项 + id**，**没有"姓名"列**——注册时未设该字段（FR-S-13 规则 2 / 验收 2）。
- `defaultPlace` 未填时返回字符串 `"未设置"`，与买家端 `/api/customer/me` 口径一致（验收 3）。

| 场景 | 状态码 | 响应 |
| --- | --- | --- |
| 已登录 | 200 | 上述结构 |
| 未登录 | 401 | `{"error":"未登录"}` |

### 2.2 `GET /api/admin/customers/{id}/orders`（FR-S-14）

参数同上。响应在分页字段外多带 `customerId`、`username`（供页面标题显示）：

```json
{ "items": [ { "id": 1, "productId": 1, "productName": "冒烟商品",
              "submittedAt": "...", "result": "成功", "closedAt": "..." } ],
  "page": 1, "size": 10, "total": 1, "totalPages": 1,
  "customerId": 3, "username": "smoke_..." }
```

| 场景 | 状态码 | 响应 |
| --- | --- | --- |
| 已登录 | 200 | 上述结构 |
| 未登录 | 401 | `{"error":"未登录"}` |
| 客户不存在 | 404 | `{"error":"客户不存在"}` |

## 3. 关键实现决策

### 3.1 购买历史的查询与买家端逐字一致

```java
intents.findByCustomerIdAndStageOrderBySubmittedAtDescIdDesc(customer.getId(), IntentStage.closed);
```

这与 `CustomerService.history()`（买家端 FR-C-07）用的是**同一个查询、同一套结果映射、同一个"成功之外一律记失败"的换算**。

原因：FR-S-14 验收标准第 3 条要求"与 FR-C-07 中该客户自己看到的记录集合一致"。若两边各写一份判断，迟早会漂——现在改任一处都必须同时改另一处，或者直接改不动。

### 3.2 排序放在内存里，不交给 SQL

`registered_at` 是 ISO-8601 字符串，毫秒为 0 时会少一段小数（如 `...T02:32:42Z` vs `...T02:32:42.316Z`），交给 SQLite 排序会让**同一秒注册**的两条记录排错序。故改为取出后在内存按 `(registeredAt DESC, id DESC)` 排序，用自增 id 兜底——与 `IntentRepository` 里"队列顺序用 `(submittedAt, id)` 决定"是同一套思路。

客户量在本项目规模下不构成性能问题。

### 3.3 无表结构变更

只读 `customer` / `intent` / `product` 三张既有表，不加字段、不加索引、不加表。`ddl-auto=update` 本轮不会改动任何东西。

### 3.4 前端自校验登录

两个页面在加载时先请求 `GET /api/auth/session`，401 即跳 `/login.html`——与 `admin.html` 由服务端 302 跳转的效果一致。

因此即便直接用 URL 打开这两个独立页面，权限也是保住的；后台导航入口（见第 6 节）只是多一条走得到的路。

### 3.5 UI 风格与既有页面统一

首版两个独立页面照买家端 `orders.html` 写，复核后发现客户列表与购买历史属于卖家后台，同域页面应是 `admin.html`，已全部改回后台风格：去掉 `login-main` 窄栏与内联样式，表格改用后台既有 `.table-wrap > table`，交易结果不做红绿着色，脚本抽为外部文件（`customers.js` / `customer-purchases.js`），分页文案与 `admin.js` 的 `loadInventory` 对齐。后台页签内的客户表格本就是后台风格，独立页与之保持一致，同一功能两个入口观感才统一。

## 4. 验收对照

本机 `java -jar target/shopping-system-1.0.0.jar --server.port=3900` 起服务，走真实交易链路实测：

| SRS 验收标准 | 实测结果 |
| --- | --- |
| FR-S-13-1 新注册但未下单的客户也出现 | 注册后立刻出现在列表（客户 id=1、2，均未下单） |
| FR-S-13-2 字段为用户名/电话/默认交易地点/注册时间，无"姓名" | 返回键集合 = `{id, username, phone, defaultPlace, registeredAt}` |
| FR-S-13-3 未填地点显示"未设置"或空，不报错 | 返回 `"defaultPlace":"未设置"` |
| FR-S-13-4 点击某客户可进入购买历史页 | 列表按钮跳 `/customer-purchases.html?id={id}`，页面 200 |
| FR-S-13-5 无编辑/禁用/删除/导出/搜索/筛选入口 | 操作列只有"查看购买历史"一个按钮 |
| FR-S-14-1 只看到成功与失败的记录 | 排队中查得 `total=0`；交易中查得 `total=0`；标记成功后 `total=1`；再标记一单失败后 `total=2`（成功 + 失败） |
| FR-S-14-2 四项字段，无价格/数量/地点 | 返回键集合 = `{id, productId, productName, submittedAt, result, closedAt}` |
| FR-S-14-3 与买家端记录集合一致 | 卖家端与 `/api/customer/orders` 的 `(id, productName, result)` 三元组**完全相等** |
| 前置条件：已登录卖家 | 未登录带 cookie 缺失访问 → `401 {"error":"未登录"}` |
| AC-18 新注册客户未下单 → 出现在客户列表 | 通过 |

另：客户 id 不存在 → `404 {"error":"客户不存在"}`；两个页面均可访问（200）。
