## 1. 任务范围

1. **提交购买意向（#13973）**：必须登录客户账号才能提交；一单固定 1 件；提交即生成一条下单记录并挂在账号下，下单时间 = 提交时间；同一账号可对同一商品重复提交、不去重；提交不预占、不扣减库存；已冻结、已下架商品不能提交；原口令码入口废除。
2. **发起交易（#13980）**：卖家主动发起，系统强制取队首（最早提交且未终结），一次只对一人、只卖 1 件，不能挑选；发起后该商品自动冻结并停止接受新意向，不影响其他商品；本版不提供手动冻结/解冻。
3. **标记交易成功（#13981）**：库存减 1；仍有剩余则回在售，归零则进入已售终态（补货也不恢复）并计入历史商品；不得超卖；该笔意向记为成功、交易时间 = 标记时间；同一客户在该商品的其余未终结意向一并作废。
4. **标记交易失败（#13982）**：商品恢复在售且**不自动递补**；选"作废"则该意向记为失败，选"重新排队"则旧记录结案、新记录入队尾且下单时间刷新；失败不扣库存；发生过交易失败的商品计入历史商品。
5. **手动下架商品（#13978）**：在售或已冻结商品都可下架，库存为 0 的商品由系统自动下架；下架后买家端立即不可见、详情不可访问、不能提交意向；未终结意向须由卖家选择作废或重新排队；手动下架为终态，不进历史、无重新上架入口。
6. **售罄补货并重新上架（#13979）**：仅适用于售罄下架（库存归零且未成交）的商品，已售终态不适用；库存由 0 调为正数后商品仍为已下架，须再执行重新上架才回到在售；重新上架后重新接收意向，原队列不恢复。

## 2. 后端实现

### 2.1 新增文件

| 文件（`src/main/java/com/coursewise/shopping/` 下） | 职责 |
|---|---|
| `trade/TradeService.java` | 交易模块全部业务：提交意向、发起交易、标记成功/失败、手动下架、售罄补货、重新上架、历史商品（561 行） |
| `trade/TradeController.java` | 交易模块 REST API（见 2.2，115 行） |

### 2.2 REST API

| 方法与路径 | 说明 | 鉴权 |
|---|---|---|
| `POST /api/customer/intents` | 提交购买意向，成功 201，返回 `id / position / submittedAt / stock` | 客户 Cookie |
| `GET /api/customer/intents` | 当前客户进行中的下单（排队中 / 交易中） | 客户 Cookie |
| `GET /api/admin/trades` | 交易工作台：在售 / 冻结 / 售罄商品及各自队列 | 卖家 Cookie |
| `GET /api/admin/trades/{id}` | 单商品交易详情（含队列与交易中意向） | 卖家 Cookie |
| `POST /api/admin/trades/{id}/start` | 发起交易，强制取队首 | 卖家 Cookie |
| `POST /api/admin/trades/{id}/success` | 标记交易成功 | 卖家 Cookie |
| `POST /api/admin/trades/{id}/fail` | 标记交易失败，`disposition` = `void` / `requeue` | 卖家 Cookie |
| `POST /api/admin/products/{id}/withdraw` | 手动下架，`disposition` = `void` / `requeue` | 卖家 Cookie |
| `POST /api/admin/products/{id}/restock` | 售罄补货，`stock` 为正整数 | 卖家 Cookie |
| `POST /api/admin/products/{id}/relist` | 重新上架（需库存 > 0） | 卖家 Cookie |
| `GET /api/admin/product-history` | 历史商品（发生过交易结果的成功 / 失败） | 卖家 Cookie |

提交意向响应示例：

```json
{ "id":12, "productId":3, "submittedAt":"2026-10-30T08:22:06.294Z",
  "position":4, "stock":3 }
```

错误码口径：未登录 `401`、参数非法 `400`、商品不存在 `404`、商品不可买（冻结 / 下架 / 售罄）`409`。

## 3. 数据库

数据库为 SQLite 单文件 `data/shop.db`，由 Hibernate 按 `ddl-auto=update` 启动时自动建表/补列，**无需手工执行 SQL 脚本**。本次**没有新增表，也没有新增字段**——只使用了既有字段：

| 表 | 字段 | 本次用法 |
|---|---|---|
| `product` | `status` | 使用既有枚举 `active` / `resumed` / `frozen` / `sold` / `depleted` / `withdrawn`，未新增取值 |
| `product` | `stock` | 成交时减 1；提交意向时只读不写 |
| `product` | `trading_intent_id` | 发起交易时指向队首意向，结果标记后置空 |
| `product` | `result` / `result_at` | 成功写 `success`、失败写 `fail`；手动下架与售罄时清空，因此二者天然不进历史商品 |
| `intent` | `customer_id` | 提交意向时写入当前账号，至此 `intent` 与 `customer` 打通 |
| `intent` | `stage` / `outcome` / `closed_at` | 队列状态、结局（success / voided / requeued / unsold / cancelled）、交易时间 |

**为什么不需要迁移**：`withdrawn`、`depleted`、`customer_id`、`result` 等字段在账户模块与商品模块升级时已建好，本模块只是把它们接上业务入口；实体类与建表逻辑一行未改，队友的代码不受影响。

### 3.1 既有代码的最小必需改动

- `repository/IntentRepository.java`：新增 `findByCustomerIdAndStageInOrderBySubmittedAtDescIdDesc`（"我的订单"进行中记录）。
- `repository/ProductRepository.java`：新增 `findByStatusInOrderByIdDesc`（交易工作台取数）、`findByResultIsNotNullOrderByResultAtDescIdDesc`（历史商品）。
- 未改动任何既有 Service、实体类与业务规则。

## 5. 并发与一致性

- 交易模块所有写操作统一走 `TradeService.write()`：`ReentrantLock(true)` 包住 `TransactionTemplate`，**锁在事务提交之后才释放**，使"读队列 → 改状态 → 提交"整体串行。
- 由此保证同一商品同一时刻至多一条"交易中"意向：后台开两个标签页同时点"发起交易"，第二个请求只会取到下一位。
- 队列顺序为 `(submitted_at, id)` 升序；位次实时计算、不落库，有人撤销或作废后自动前移，不出现空号。

## 7. 与其他需求的衔接

- **依赖账户模块**：提交意向通过 `customer_session` 取当前账号，写入 `intent.customer_id`；账户模块（FR-C-04/05/07）不需要为本模块做任何改动。
- **依赖商品模块**：只读取 `product.stock` 与 `product.status`；商品模块的"库存调 0 自动售罄"是售罄状态的产生入口，本模块负责其后的补货与重新上架。
- **与测试的分工**：正式测试用例与测试报告由测试同学（谭梓良）负责；本文第 6 节是交付前的界面自检，不作为测试报告。

## 8. 运行方式

```powershell
cd se-course-project
.\mvnw.cmd spring-boot:run     # 买家 / ，后台 /admin.html（admin / admin1234）
.\mvnw.cmd test                # 既有集成测试（23 项）
```

演示顺序：注册两个客户 → 卖家发布商品（库存 3）→ 客户提交意向（其中一个提交两次）→ 后台"交易管理"发起交易 → 标记成功（库存 3→2）→ 再次发起 → 标记失败·重新排队 → 手动下架 → 发布库存 1 的商品并成交至 0（已售终态）→ 另发一件并把库存改 0（售罄）→ 补货 → 重新上架。
